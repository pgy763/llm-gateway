# 03 · 状态机设计详解

这是整个项目里最核心的部分。如果你只想精读一篇文档，就读这篇。

---

## 一、先用一个生活例子理解"状态机"

想想你在外卖 App 上点一单饭，订单会经历这些状态：

```
已下单 → 商家接单 → 骑手已取货 → 配送中 → 已送达
```

这里面有两个东西：

- **状态**：订单现在处于哪一步（"配送中"）
- **事件**：发生了什么导致它变化（"骑手点了取货"）

**关键规则是：不能乱跳。**

比如：

- 订单在"已送达"之后，还能不能变回"配送中"？**不能。** 都已经吃上了。
- 订单在"已下单"时，能不能直接跳到"已送达"？**不能。** 中间骑手总得跑一趟。

这两条规则如果没写好，就会出现很荒诞的情况：订单显示"已送达"，但骑手还在路上。

**状态机就是把这套规则明确规定下来的一张表。**

## 二、为什么需要它：不用状态机会怎样

先看不用状态机的写法。假设任务是"生成一篇文章"，你大概会这么写：

```java
public class Task {
    private String status;   // "生成中" / "已完成" / "已失败" ...
}

// 生成完成的回调里
task.setStatus("已完成");

// 审查不通过的处理里
task.setStatus("生成中");   // 退回去重写

// 用户取消的处理里
task.setStatus("已取消");
```

**看起来没问题。但它埋了至少三个雷：**

### 雷 1：状态可能会互相矛盾

假设用户点了"取消"，任务变成 `已取消`。
但此时后台的生成线程刚好跑完了，它并不知道用户取消了，于是又执行了一次：

```java
task.setStatus("已完成");   // 覆盖了"已取消"
```

结果：用户明明取消了，任务却完成了。

### 雷 2：可能出现"不可能的状态"

某段代码写错了，把 `"已完成"` 打成了 `"完成已"`。
编译器不会报错（它只是个字符串），程序照常运行。
直到某天你查数据库，发现有几个任务的 `status` 是个从没见过的值。

### 雷 3：说不清"为什么变成这样"

线上出问题时你看到的只有一行：`status = 已失败`。

**为什么会失败？** 是模型调用失败了？还是审查三次都没过？还是程序崩了？

信息全丢了，只能靠猜。

## 三、状态机的三个基本概念

### 概念 1：状态（State）—— 必须是封闭的

**封闭**的意思是：状态只有这几种，没有别的可能。

代码里用枚举（`enum`）来实现：

```java
// domain/task/TaskState.java
public enum TaskState {
    CREATED,      // 已创建，排队等待
    GENERATING,   // 正在生成内容
    REVIEWING,    // 正在审查
    RETRYING,     // 待重写
    FINALIZING,   // 正在定稿
    COMPLETED,    // 已完成（终态）
    FAILED,       // 已失败（终态）
    CANCELLED     // 已取消（终态）
}
```

**用枚举而不是字符串，好处是白拿的：**

| 用字符串 `String status` | 用枚举 `TaskState state` |
| --- | --- |
| 拼错了编译器不报错 | 拼错了编译直接失败 |
| 不知道一共有几种取值，得全局搜索 | 打开文件就能看完 |
| 无法附加行为（比如判断是不是终态） | 可以加方法，见下面 |

枚举还可以带方法：

```java
/** 是不是终态 */
public boolean isTerminal() {
    return this == COMPLETED || this == FAILED || this == CANCELLED;
}
```

于是判断"任务是不是跑完了"就有了唯一答案，不用每个地方各写一遍 if。

---

### 概念 2：事件（Event）—— 状态不会自己变

状态变化必须由某个事件触发。把事件也定义成枚举：

```java
// domain/task/TaskEvent.java
public enum TaskEvent {
    START,          // 开始处理
    GENERATED,      // 生成完成
    REVIEW_PASS,    // 审查通过
    REVIEW_REJECT,  // 审查不通过
    RETRY,          // 开始重写
    FINALIZE,       // 定稿完成
    FAIL,           // 发生错误
    CANCEL          // 用户取消
}
```

**为什么要单独定义事件，而不是直接改状态？**

因为这样每次状态变化都能回答"**是因为发生了什么**"。

日志里可以写成：

```
任务 task-abc 收到事件 START，状态 CREATED → GENERATING
任务 task-abc 收到事件 GENERATED，状态 GENERATING → REVIEWING
任务 task-abc 收到事件 REVIEW_REJECT，状态 REVIEWING → RETRYING
```

排查问题时，这一串记录比"当前状态是什么"有用得多。

---

### 概念 3：迁移表（Transition Table）—— 规则集中写一处

这是状态机的心脏，也是整个项目里最重要的几十行代码。

```java
// domain/task/TaskStateMachine.java
private static Map<TaskState, Map<TaskEvent, TaskState>> TRANSITIONS = buildTransitions();
```

读法：**"在状态 A 下，如果收到事件 E，就变成状态 B。"**

完整展开就是这样一张表：

| 当前状态 | 收到事件 | 变成 | 含义 |
| --- | --- | --- | --- |
| CREATED | START | GENERATING | 开始处理 |
| CREATED | CANCEL | CANCELLED | 还没开始就被取消 |
| GENERATING | GENERATED | REVIEWING | 初稿写完，送去审查 |
| GENERATING | FAIL | FAILED | 生成过程中出错 |
| GENERATING | CANCEL | CANCELLED | 生成中途被取消 |
| REVIEWING | REVIEW_PASS | FINALIZING | 审查通过，去定稿 |
| REVIEWING | REVIEW_REJECT | RETRYING | 审查没过，准备重写 |
| REVIEWING | FAIL | FAILED | 审查环节出错 |
| RETRYING | RETRY | GENERATING | 开始重写（回到生成） |
| RETRYING | FAIL | FAILED | 重写前出错 |
| RETRYING | CANCEL | CANCELLED | 重写前被取消 |
| FINALIZING | FINALIZE | COMPLETED | 定稿完成 |
| FINALIZING | FAIL | FAILED | 定稿环节出错 |
| COMPLETED | —— | —— | **终态，没有任何出边** |
| FAILED | —— | —— | **终态，没有任何出边** |
| CANCELLED | —— | —— | **终态，没有任何出边** |

**表上没有的组合，就是非法的。**

比如 `CREATED` + `FINALIZE` 查不到，说明"任务刚创建就直接定稿"是不允许的。
这时代码会抛异常：

```java
public static TaskState next(TaskState from, TaskEvent event) {
    TaskState to = edgesOf(from).get(event);
    if (to == null) {
        throw new IllegalTaskTransitionException(from, event);
    }
    return to;
}
```

异常信息写得很具体，直接告诉你当前允许哪些事件：

```
非法的状态迁移：任务当前是 [已创建]，无法响应事件 [FINALIZE]。
当前允许的事件有：[START, CANCEL]
```

## 四、可视化的状态流转图

```
                      ┌───────────┐
                      │  CREATED  │
                      │  已创建   │
                      └─────┬─────┘
                            │ START
                            ▼
                      ┌───────────┐
              ┌──────▶│GENERATING │◀──────┐
              │       │  生成中   │       │
              │       └─────┬─────┘       │
              │             │ GENERATED   │ RETRY
              │             ▼             │
              │       ┌───────────┐       │
              │       │ REVIEWING │       │
              │       │  审查中   │       │
              │       └─────┬─────┘       │
              │             │             │
              │    REVIEW_REJECT          │
              │             ▼             │
              │       ┌───────────┐       │
              └───────│ RETRYING  │───────┘
                      │  待重写   │
                      └───────────┘
                      
              REVIEW_PASS │
                          ▼
                    ┌───────────┐
                    │FINALIZING │
                    │  定稿中   │
                    └─────┬─────┘
                          │ FINALIZE
                          ▼
                    ┌───────────┐
                    │ COMPLETED │  ← 终态
                    │  已完成   │
                    └───────────┘

  任意进行中状态收到 FAIL   → FAILED    （终态）
  任意进行中状态收到 CANCEL → CANCELLED （终态）
```

注意那个**回环**（`GENERATING → REVIEWING → RETRYING → GENERATING`）：
这就是"审查不通过就打回重写"的实现。

**它不是死循环**，因为有一个计数器管着：

```java
public void markReviewRejected(String comment) {
    this.lastReviewComment = comment;
    if (canRetry()) {                    // retryCount < maxRetry
        fire(TaskEvent.REVIEW_REJECT);   // REVIEWING -> RETRYING
        fire(TaskEvent.RETRY);           // RETRYING  -> GENERATING
    } else {
        this.lastError = "重写 " + maxRetry + " 次后仍未通过审查...";
        fire(TaskEvent.FAIL);            // REVIEWING -> FAILED
    }
}
```

> **这是状态机的一个关键设计原则：**
> 状态机只管"允不允许这么走"，业务规则（比如"最多重试几次"）放在领域对象里。
> 两者各司其职，不要混在一起。

## 五、代码在哪，怎么读

如果你想快速看懂这部分，按这个顺序读：

### 第 1 步：看状态和事件的定义

```
domain/task/TaskState.java      8 个状态，带 isTerminal() 方法
domain/task/TaskEvent.java      8 个事件
```

两分钟能看完。

### 第 2 步：看迁移表

```
domain/task/TaskStateMachine.java   ← 核心，重点看 buildTransitions() 方法
```

看的时候注意：**终态故意没有出边。**

```java
// COMPLETED / FAILED / CANCELLED 是终态，故意不给它们任何出边。
// 这意味着：任务一旦完成，就无法被任何事件"唤醒"回去，杜绝了脏状态。
```

### 第 3 步：看谁在使用它

```
domain/task/AiTask.java           领域对象，所有状态变化的唯一入口
application/TaskService.java      实际驱动状态机往前走
```

`AiTask` 里有一个关键约束：**状态字段是私有的，外部改不了。**

```java
@Getter                    // 只生成 getter，没有 setter
public class AiTask {
    private TaskState state;      // 外部无法直接赋值

    /** 唯一的状态修改入口 */
    public TaskState fire(TaskEvent event) {
        this.state = TaskStateMachine.next(this.state, event);
        // ...
    }
}
```

用 `@Getter` 而不是 `@Data`（`@Data` 会连 setter 一起生成），
这样编译期就保证了"没人能绕过状态机改状态"。

## 六、拿到运行结果里能看到什么

调用任务的 `history` 接口，能看到完整的流转记录：

```bash
curl http://localhost:8080/v1/tasks/task-abc123/history
```

```json
{
  "code": 0,
  "data": [
    { "fromState": null,        "toState": "CREATED",    "event": "STATE_REFRESH", "detail": "任务已创建：写一篇..." },
    { "fromState": "CREATED",   "toState": "GENERATING", "event": "START",         "detail": "开始处理" },
    { "fromState": "GENERATING","toState": "REVIEWING",  "event": "GENERATED",     "detail": "初稿生成完成，共 312 字" },
    { "fromState": "REVIEWING", "toState": "RETRYING",   "event": null,            "detail": "审查未通过：内容过短，312 字..." },
    { "fromState": "RETRYING",  "toState": "GENERATING", "event": "RETRY",         "detail": "开始第 1 次重写" },
    { "fromState": "GENERATING","toState": "REVIEWING",  "event": "GENERATED",     "detail": "初稿生成完成，共 486 字" },
    { "fromState": "REVIEWING", "toState": "FINALIZING", "event": "REVIEW_PASS",   "detail": "审查通过：长度 486 字，检查通过" },
```

比如用户投诉"我这个任务怎么花了三次才生成好"，你打开这个接口一看就明白了 ——
前两次是因为内容太短被审查打回了。不用去猜，也不用翻日志。

## 七、为什么这么设计：三个决策点

### 决策 1：为什么用"事件驱动"而不是"直接改状态"

直接改状态是这样：

```java
task.setStatus(RETRYING);
```

事件驱动是这样：

```java
task.fire(TaskEvent.REVIEW_REJECT);
```

后者多了一层间接。值得吗？

**值得，因为它强制你回答一个问题：这次变化是因为什么？**

当你被迫写下 `REVIEW_REJECT` 时，你自然会去想：
"审查不通过之后该往哪走？还有重试机会吗？"
这些思考如果省略了，就会变成散落各处的 if-else。

### 决策 2：为什么拒绝非法迁移时要抛异常，而不是打日志继续

有人会想：打条日志，然后忽略这次操作，程序不是更"健壮"吗？

**不是。** 非法迁移意味着**调用方的逻辑写错了**。

如果只是打日志继续，这个错误会被埋起来，然后变成一条脏数据躺在数据库里。
三个月后有人发现它，没有任何线索能定位到是哪段代码写错的。

抛异常则是当场暴露：错误信息里带着状态和事件，堆栈直接指到出错的代码行。

> 原则：**能当场发现的错误，不要留到以后。**
> 这类"快速失败"（fail-fast）的设计，在长期维护里能省下大量排查时间。

### 决策 3：为什么状态机逻辑放在领域对象里，而不是 Service 里

对比两种写法：

**写法 A（放在 Service 里）：**
```java
// TaskService.java
if (task.getRetryCount() < task.getMaxRetry()) {
    task.setState(TaskState.RETRYING);
} else {
    task.setState(TaskState.FAILED);
}
```

**写法 B（放在领域对象里，本项目采用）：**
```java
// TaskService.java
task.markReviewRejected(comment);   // 规则封装在对象内部

// AiTask.java
public void markReviewRejected(String comment) {
    if (canRetry()) { ... } else { ... }
}
```

区别在哪？

写法 A 的问题：**这条规则会重复出现。**
今天在 `TaskService` 里写一遍，明天定时补偿任务里可能又要写一遍，
后天加个"管理员手动重试"的功能，还得再写一遍。
**三份代码，迟早会出现不一致。**

写法 B 把规则收在一个地方。谁要触发"审查不通过"，都调这同一个方法。

> 这就是"贫血模型"和"充血模型"的区别。
> 贫血模型里，对象只是一堆 getter/setter，规则全散在 Service 里。
> 充血模型里，对象自己管自己的规则。
>
> 对于规则简单 CRUD 场景，贫血模型就够了，别硬上。
> 但像这种有明确状态流转的场景，充血模型明显更合适。

## 八、怎么扩展这个状态机

### 场景：想加一个"人工审核"环节

需求：有些任务风险高，生成完不直接完成，而是等一个人工审核。

**第 1 步**：加状态

```java
public enum TaskState {
    // ...
    PENDING_REVIEW,   // 待人工审核（新增）
    REJECTED_BY_HUMAN // 人工驳回（新增，终态）
}
```

**第 2 步**：加事件

```java
public enum TaskEvent {
    // ...
    HUMAN_APPROVE,    // 人工通过
    HUMAN_REJECT      // 人工驳回
}
```

**第 3 步**：在迁移表里加两条边

```java
table.put(TaskState.FINALIZING, Map.of(
        TaskEvent.FINALIZE, TaskState.COMPLETED,
        TaskEvent.HUMAN_REVIEW_REQUIRED, TaskState.PENDING_REVIEW,   // 新增
        TaskEvent.FAIL, TaskState.FAILED
));

table.put(TaskState.PENDING_REVIEW, Map.of(                          // 新增
        TaskEvent.HUMAN_APPROVE, TaskState.COMPLETED,
        TaskEvent.HUMAN_REJECT, TaskState.REJECTED_BY_HUMAN
));
```

**完成。** 其他代码一行都不用改 —— 因为状态机已经把规则集中管起来了。

**这就是把规则集中写一处带来的好处：加需求不用满项目找 if-else。**

---

## 九、一句话总结

> 状态机做的事，是把"**什么情况下能做什么**"从散落各处的 if-else，
> 变成一张**集中的、可验证的、改一处就生效的**表。
>
> 它换来的是：不可能的状态产生不了，出问题了能完整还原，
> 加需求不用翻遍整个项目。
