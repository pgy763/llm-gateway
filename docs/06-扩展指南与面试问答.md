## 第一部分：怎么扩展这个项目

### 场景 1：接入一个新的模型厂商

假设要接入"智谱 GLM"，它的接口也是 OpenAI 兼容格式。

**只需要改配置，一行代码都不用写：**

```yaml
# application.yml
gateway:
  providers:
    - name: zhipu
      type: openai-compatible          # 复用已有的适配器
      base-url: https://open.bigmodel.cn/api/paas/v4
      api-key: ${ZHIPU_API_KEY:}
      models:
        - glm-4-plus
        - glm-4-air
      priority: 2
      enabled: true
      timeout-ms: 60000
```

**如果这家厂商的接口格式完全不同呢？**（比如不是 OpenAI 兼容的）

那就写一个新的适配器实现：

```java
// 1. 在 domain/provider/ 下新建一个类
public class ZhipuNativeProvider implements ChatProvider {

    @Override
    public String name() {
        return config.getName();
    }

    @Override
    public boolean supports(String model) {
        return config.getModels().contains(model);
    }

    @Override
    public ChatResponse chat(ChatRequest request, String model) {
        // 把统一的 ChatRequest 转成智谱的格式
        // 发请求
        // 把智谱的响应转回统一的 ChatResponse
    }

    @Override
    public TokenUsage chatStream(ChatRequest request, String model,
                                 Consumer<String> onDelta) {
        // 同上，但用流式方式解析
    }
}
```

```java
// 2. 在 ProviderRegistry.create() 里注册
private ChatProvider create(ProviderConfig config) {
    return switch (type) {
        case "mock" -> new MockProvider(config);
        case "openai-compatible" -> new OpenAiCompatibleProvider(config);
        case "zhipu-native" -> new ZhipuNativeProvider(config);   // ← 加这一行
        default -> throw new IllegalStateException("不支持的类型：" + type);
    };
}
```

**完成。** 业务代码、状态机、限流、记账全都不用动 —— 因为它们只依赖 `ChatProvider` 接口。

> **这就是"适配器模式"的价值。**
> 面试时如果被问"你怎么保证扩展性"，这就是最有力的回答：
> **因为新增一家厂商的改动量是"1 个新文件 + 1 行注册"，而不是"改遍所有调用点"。**

### 场景 2：给任务状态机加一个"人工审核"环节

需求：生成的内容不直接完成，而是先给人工看一眼。

**三步搞定：**

```java
// 第 1 步：加状态
public enum TaskState {
    // ... 原有状态
    PENDING_REVIEW,      // 待人工审核
    REJECTED_BY_HUMAN;   // 人工驳回（终态）
}
```

```java
// 第 2 步：加事件
public enum TaskEvent {
    // ... 原有事件
    HUMAN_APPROVE,       // 人工通过
    HUMAN_REJECT;        // 人工驳回
}
```

```java
// 第 3 步：在迁移表里加边
private static Map<TaskState, Map<TaskEvent, TaskState>> buildTransitions() {
    // ...
    table.put(TaskState.FINALIZING, Map.of(
            TaskEvent.FINALIZE, TaskState.COMPLETED,
            TaskEvent.HUMAN_REVIEW_REQUIRED, TaskState.PENDING_REVIEW,  // 新增
            TaskEvent.FAIL, TaskState.FAILED
    ));

    table.put(TaskState.PENDING_REVIEW, Map.of(                         // 新增整块
            TaskEvent.HUMAN_APPROVE, TaskState.COMPLETED,
            TaskEvent.HUMAN_REJECT, TaskState.REJECTED_BY_HUMAN
    ));
    // ...
}
```

然后加一个接口让人工审核结果能够送进来：

```java
@PostMapping("/v1/tasks/{taskId}/review")
public ApiResponse<TaskView> humanReview(@PathVariable String taskId,
                                         @RequestParam boolean approved,
                                         @RequestParam(required = false) String comment) {
    taskService.humanReview(taskId, approved, comment);
    return ApiResponse.ok(TaskView.from(taskService.getEntity(taskId)));
}
```

**注意**：加完状态和事件之后，`TaskStateMachineTest` 里那个
"终态不可逆"的测试会自动覆盖到新终态（因为它遍历 `TaskEvent.values()`），
不需要额外维护。这就是把规则集中管理带来的好处。

### 场景 3：把规则审查换成模型审查（Critic 模式）

现在 `TaskService.reviewContent()` 用的是简单规则（检查长度）。

要换成"让另一个模型来打分"，只需要改这一个方法：

```java
private ReviewResult reviewContent(String content) {
    // 用一次独立的模型调用做审查
    ChatRequest reviewRequest = new ChatRequest();
    reviewRequest.setMessages(List.of(
            ChatMessage.system("""
                    你是一个严格的内容审查员。请检查下面这段内容：
                    1. 是否跑题
                    2. 是否有事实性错误
                    3. 是否有前后矛盾

                    只输出 JSON，格式：{"passed": true/false, "reason": "原因"}
                    """),
            ChatMessage.user(content)
    ));

    ChatResponse response = callModel(reviewRequest);
    // 解析 JSON 拿到结论
    // ...
}
```

**状态机完全不用改** —— 因为它只关心 `ReviewResult` 是 pass 还是 reject，
不关心这个结论是规则算出来的还是模型算出来的。

> 这是"依赖抽象而不是实现"的又一个例子。

## 第二部分：面试常见问题与回答要点

这一节是给你自己看的。**回答要点写的是思路，不是逐字稿 —— 照着背会很假。**

---

### Q1：介绍一下这个项目

**不要这么答**："我写了一个 Spring Boot 项目，用了 Redis 和 PostgreSQL，实现了大模型调用……"

**建议这么答**（按"问题 → 方案 → 难点"的结构）：

> 这个项目解决的是"多个业务系统各自直连大模型"带来的一系列问题：
> 密钥散落、厂商故障没有备份、用量无法分摊、缺限流、长任务会丢。
>
> 我的做法是做一层网关：业务系统只认网关，由网关负责鉴权、限流、路由降级和记账。
>
> 其中比较有意思的是多步任务的编排 —— 生成一篇文章要经过"生成→审查→重写"多个阶段，
> 我用状态机来管这个流程，状态持久化在数据库里，所以服务重启后任务能接着跑。

---

### Q2：这个跟直接调大模型 API 有什么区别？

**核心回答**：区别在于"去掉 AI 调用那一行，项目还剩下什么"。

> 如果只是把请求转发给大模型再返回，那确实就是个反向代理，二十行代码就能写完。
>
> 这个项目的价值在调用前后：
> - 调用前要做鉴权、限流、配额校验、选出可用的提供方
> - 调用后要做熔断记录、降级切换、token 计量、审计日志
>
> 另外任务编排那一整块（状态机、持久化、补偿扫描、乐观锁）跟 AI 完全无关，
> 它是个纯粹的流程管理问题。

**如果面试官继续追问"这不还是套壳吗"**，可以这样回应：

> 判断标准很简单：把 DeepSeek 换成通义，业务代码要改几行？
> 在我这个项目里是零行 —— 改配置文件就行。
> 如果是套壳，模型地址和解析逻辑是散在业务代码里的，换一家要改好几处还要回归测试。

---

### Q3：为什么要用状态机？直接用一个 status 字段不行吗？

**回答要点**（三层递进）：

> 短期看是能用的。但有三类问题：
>
> 1. **状态会互相矛盾**。比如用户取消了任务，但后台的生成线程刚跑完，
>    又把状态改成了"已完成"。
> 2. **会出现不存在的状态**。字符串拼错了编译器不报错，要到线上才发现。
> 3. **出问题查不清**。只知道"它失败了"，不知道是因为模型报错、
>    还是审查三次没过、还是程序异常。
>
> 用状态机之后：
> - 所有合法迁移集中写在一张表里，表上没有的直接拒绝
> - 用枚举代替字符串，拼错编译就报错
> - 每次迁移都记一条日志，任何异常都能完整还原

---

### Q4：降级链是怎么实现的？什么情况下会重试？

> 按优先级排出一条链，比如 `deepseek → kimi → mock`，依次尝试。
>
> **关键是区分错误类型**：
> - 超时、429、5xx → 是对方的问题，换一家可能就好了，继续降级
> - 400、401、403 → 是我自己的问题，换一家结果一样，直接失败
>
> 这个判断很重要。如果不区分，参数写错也会白烧三家的额度。

---

### Q5：流式模式下怎么降级？（这道题有难度）

**这是一道很好的区分题。** 答得好能明显加分。

> 这里有个绕不过去的限制：**如果已经往客户端推了半段内容，就不能再降级了。**
>
> 因为两个模型写的上下文接不上，用户会看到前后矛盾的两段内容。
>
> 我的做法是记一个 `alreadyEmitted` 标志：
> - 还没输出过内容 → 正常降级，换下一家重新生成
> - 已经输出过了 → 只能如实报错终止
>
> 这背后是一个更普遍的判断：**副作用一旦发生就不可逆。**
> 降级的前提是"这次尝试可以完整重来"，一旦对外产生了可见的影响，就无法回退了。

---

### Q6：限流为什么用令牌桶？为什么算法要写在 Lua 里？

> **不用简单计数器的原因**是临界问题：
> 用户在 12:00:59 打满 60 次，12:01:00 又打满 60 次，两秒内灌进来 120 次。
> 令牌桶没这个问题，因为令牌是按速率真实"生产"出来的，不会因为时间窗口切换而凭空多出来。
>
> 同时令牌桶还允许正常的突发流量 —— 桶里攒的令牌可以用来吸收高峰，
> 这对真实业务是必要的（用户点击本来就不是匀速的）。
>
> **写在 Lua 里是为了原子性。**
> "读令牌 → 判断 → 扣减 → 写回"这四步如果分四条命令发，
> 两个并发请求可能同时读到"还剩 1 个"，然后都放行，导致超发。
> Redis 执行 Lua 是原子的，不会被其它命令打断。

---

### Q7：熔断和降级有什么区别？

> **降级是"这次请求"的策略**：这家失败了，我换一家。
> **熔断是"一段时间内"的策略**：这家一直在失败，我先不试它了。
>
> 为什么需要熔断？因为如果主模型挂了、超时设置又是 60 秒，
> 那么每个请求都要先白等 60 秒才能切到备用。
> 这比直接失败还难受。
>
> 熔断的做法是：连续失败 3 次就拉黑 30 秒，期间直接跳过它。
> 30 秒后自动恢复尝试 —— 万一它已经好了。

---

### Q8：为什么用乐观锁？什么场景该用悲观锁？

> 判断依据是**冲突的频率**。
>
> 这个项目里，同一个任务被并发修改是极少见的（只有用户连点、
> 或者补偿扫描撞上正在执行的任务）。所以用乐观锁：
> 平时没有额外开销，偶发冲突时让其中一个失败重试就行。
>
> 如果是秒杀抢库存这种冲突非常频繁的场景，乐观锁会导致大量重试，
> 这时候该用悲观锁（`SELECT ... FOR UPDATE`）直接排队，
> 或者用 Redis 的原子操作来扣减。
>
> 关键不是"哪个更好"，而是"我的场景冲突多不多"。

---

### Q9：服务重启后，正在跑的任务怎么办？

> 状态是持久化的，每一步都立刻写数据库。所以重启后能知道"它停在哪"。
>
> 但要重新跑起来，还需要一个机制把中断的任务捡起来。
> 我用的是定时补偿扫描：每 2 秒找出状态是"进行中"、且超过 30 秒没更新的任务，
> 重新推进。
>
> 这里有个取舍要说清楚：用"时间阈值"判断任务是否卡住是比较粗糙的。
> 如果某个任务真的处理超过 30 秒，会被误判、重复触发一次。
> 严谨的做法是用分布式锁或任务租约。
> 我选简单方案是因为要控制项目复杂度，但我知道它的边界在哪。

> **注意最后这句话。** 主动说出方案的局限性，比被面试官问出来要好得多。
> 它传递的信号是："我知道自己在做什么，也知道更好的方案是什么"。

---

### Q10：这个项目有什么不足？如果让你继续优化会做什么？

**这道题一定要准备好，几乎必问。** 诚实回答反而加分。

> 主要有这几块：
>
> 1. **任务恢复机制不够严谨**。用时间阈值判断任务是否卡住，
>    在多实例部署时可能重复执行。应该换成分布式锁或消息队列。
> 2. **密钥是明文存储的**。真实项目应该只存哈希，创建时返回一次明文。
> 3. **管理接口没有鉴权**。现在任何人都能调 `/admin/**`。
> 4. **审查环节太简单**。现在只检查长度，应该接一个模型做打分（Critic 模式）。
> 5. **缺少全链路追踪**。虽然有 requestId，但没有接入 OpenTelemetry，
>    跨服务的调用链看不到。
> 6. **没有做压测**。限流参数、线程池大小这些配置现在是拍脑袋定的，
>    应该压测之后再定。

> **递进一下**：如果说只能优化一件事，我会先做第 1 个（任务恢复的严谨性），
> 因为那是最可能在真实环境里出数据问题的点。

## 第三部分：怎么用这个项目

### 如果是为了面试

**重点准备这三块**，其他都可以淡化：

1. **状态机的设计**（Q3）—— 能画图、能讲清为什么
2. **降级链的错误分类**（Q4）—— 能说清什么该重试什么不该
3. **流式降级的边界**（Q5）—— 这道题能答出来的人不多

**面试前建议做的准备**：

- 把项目跑起来，实际演示一次降级（用 `mock-flaky` 模型）
- 打开 `/v1/tasks/{id}/history` 接口，看看状态流转记录长什么样
- 手画一遍状态图，不看代码

### 如果是为了自己学习

建议的阅读顺序：

```
1. README.md                             了解全貌
2. docs/01-项目背景与要解决的问题.md      先想清楚"为什么要做"
3. docs/03-状态机设计详解.md              核心
4. 代码：domain/task/ 整个包              对照文档读
5. docs/04-降级熔断与限流.md              然后读代码：domain/route/ + infrastructure/ratelimit/
6. docs/05-断点续跑与并发控制.md          然后读代码：application/TaskService.java
7. 自己动手加一个场景（见本文第一部分）     最后的检验
```

**最后一步最重要。** 看懂和能改是两回事。
如果你能不看文档，自己加上"人工审核"这个状态，那说明真懂了。
