# 05 · 断点续跑与并发控制

这篇讲两个问题：

1. **服务器重启了，正在跑的任务怎么办？**
2. **两个人同时操作同一个任务，怎么办？**

---

## 一、问题从哪来

先回顾一下任务是什么：

```
用户提交："写一篇 800 字的文章"
     ↓
生成初稿（调模型，约 8 秒）
     ↓
审查（约 0.1 秒）
     ↓
不合格？→ 重新生成（又 8 秒）
     ↓
定稿完成
```

整个过程可能持续 10 到 30 秒。

**问题来了：这 30 秒里，如果服务器重启了呢？**

---

## 二、先看错误做法：状态只存内存

```java
// 反例：把状态放在内存里
private final Map<String, TaskState> taskStates = new ConcurrentHashMap<>();

public void run(String taskId) {
    taskStates.put(taskId, TaskState.GENERATING);   // 只在内存里

    String draft = generateText();                   // 花 8 秒
    // ← 就在这里服务器重启了

    taskStates.put(taskId, TaskState.REVIEWING);     // 永远不会执行到
}
```

重启后发生了什么：

- `taskStates` 这个 Map 没了
- 数据库里可能存了"任务已创建"，但没有"它跑到哪了"
- **这个任务永远卡住，没有任何机制能让它继续**

用户看到的现象：进度条卡在 60%，刷新页面也没用。

---

## 三、正确做法：状态是持久化的

本项目的做法很简单：**每走一步，立刻把状态写进数据库。**

```java
// application/TaskService.java
private void persistInternal(AiTask task, AiTaskEntity entity, TaskState before,
                             TaskEvent event, String detail) {
    entity.applyDomain(task);
    taskRepository.save(entity);         // ← 关键：立刻落库

    if (before != task.getState()) {
        writeStateLog(task.getTaskId(), before, task.getState(), event, detail);
    }
}
```

于是每一刻数据库里都有明确答案：

| 时刻 | 数据库里 state 字段的值 |
| --- | --- |
| 任务创建后 | `CREATED` |
| 开始生成时 | `GENERATING` |
| 初稿出来时 | `REVIEWING` |
| 审查没通过 | `RETRYING` → `GENERATING` |
| 完成后 | `COMPLETED` |

**重启后读数据库就知道它停在哪。** 这是"断点续跑"的基础。

但光有状态还不够 —— 状态记着 `GENERATING`，可是没有任何线程在跑它。
需要一个机制把它重新捡起来。

---

## 四、补偿扫描：谁来把中断的任务捡起来

```java
// application/TaskService.java
@Scheduled(fixedDelayString = "${gateway.task.poll-interval-ms:2000}")
public void compensateStuckTasks() {
    // ① 找出所有"还在进行中"的任务
    List<AiTaskEntity> inProgress = taskRepository.findTop50ByStateInOrderByCreatedAtAsc(
            EnumSet.of(TaskState.CREATED, TaskState.GENERATING,
                    TaskState.REVIEWING, TaskState.RETRYING, TaskState.FINALIZING));

    Instant threshold = Instant.now().minusSeconds(STUCK_THRESHOLD_SECONDS);

    for (AiTaskEntity entity : inProgress) {
        // ② 只处理"超过 30 秒没更新"的，避免打断正在正常执行的任务
        if (entity.getUpdatedAt().isBefore(threshold)) {
            log.info("补偿扫描：重新推进停滞的任务 {}", entity.getTaskId());
            gatewayTaskExecutor.execute(() -> advance(entity.getTaskId()));
        }
    }
}
```

这个机制的工作方式是：

```
每 2 秒执行一次
   ↓
问数据库：有哪些任务状态是"进行中"的？
   ↓
对每一个：它多久没动静了？
   ├─ 刚更新过（< 30 秒）→ 有人在跑，别动它
   └─ 很久没动静（> 30 秒）→ 捡起来重新推进
```

**为什么要有"30 秒"这个阈值？**

因为如果不判断，扫描会把**正在正常执行**的任务也重新启动一遍，
导致同一个任务被两个线程同时跑。

用"最后更新时间"来判断"有没有人在跑"，是一种朴素的租约机制。

> 这是本项目一个**刻意的简化**。
> 更严谨的做法是用分布式锁或者任务租约（比如给任务加一个 `lockedBy` 和 `lockExpireAt` 字段）。
> 用时间阈值的问题是：如果某个任务真的处理了超过 30 秒还没更新，
> 它会被误判为"卡住"，被重复触发一次。
>
> 好在即使发生这种情况，也不会造成数据错乱 —— 原因见下面第五节。

## 五、并发控制：乐观锁

### 场景：用户连点两下

用户在页面上点了两次"取消任务"，或者前端代码写错了，导致同一个操作被发了两次请求。

如果不做任何防护，可能发生：

```
请求 A：读到 state = GENERATING → 改成 CANCELLED → 保存
请求 B：读到 state = GENERATING → 改成 CANCELLED → 保存
```

这个例子里看起来没出问题。但换成更复杂的场景就有问题了：

```
请求 A（重写）：读到 retryCount = 1 → 生成新内容 → 写回 retryCount = 2
请求 B（取消）：读到 retryCount = 1 → 改成 CANCELLED → 写回 retryCount = 1

结果：取消成功，但重写次数丢失了一次。
```

**这叫"丢失更新"（Lost Update）** —— 后写入的覆盖了先写入的修改。

### 本项目的解法：乐观锁

在实体上加一个版本号字段：

```java
// infrastructure/persistence/entity/AiTaskEntity.java
/**
 * 乐观锁版本号。
 * 两个线程同时想改同一个任务时，谁先提交谁成功，
 * 后提交的那个会被数据库拒绝，而不是让两次修改互相覆盖。
 */
@Version
@Column(name = "version", nullable = false)
private Long version;
```

就这么一个注解，JPA 会自动实现下面这套逻辑：

```sql
-- 读的时候，把版本号一起读出来
SELECT id, state, retry_count, version FROM ai_task WHERE id = 1;
-- 假设读到 version = 5

-- 写的时候，带上版本号条件
UPDATE ai_task
   SET state = 'CANCELLED', retry_count = 1, version = 6
 WHERE id = 1 AND version = 5;
--                          ↑ 关键

-- 如果这条 SQL 影响了 0 行，说明在你读取之后，
-- 已经有别人改过它了（version 已经不是 5 了）
-- → JPA 抛出 OptimisticLockException
```

**效果**：两个并发修改中，只有一个能成功，另一个会收到明确的失败信号。
不会出现"后写的悄悄覆盖先写的"。

### 为什么用乐观锁，而不是悲观锁

悲观锁是"先锁住，再改"：

```sql
SELECT * FROM ai_task WHERE id = 1 FOR UPDATE;   -- 锁住这行
-- ... 做业务处理，可能耗时几秒 ...
UPDATE ai_task SET ... WHERE id = 1;
COMMIT;                                          -- 释放锁
```

对比一下：

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 做法 | 先锁住，别人等着 | 先改，冲突了再失败 |
| 适用场景 | **冲突频繁**，冲突概率高 | **冲突稀少**，偶尔才会撞上 |
| 代价 | 持有锁期间别人全部阻塞 | 冲突时要重试 |
| 死锁风险 | 有 | 无 |
| 数据库连接占用 | 长（整个事务期间） | 短 |

**本项目的任务修改冲突极少**（只有"用户连点"或者"补偿扫描撞上正在执行"这种偶发情况），
所以乐观锁更合适。

如果这里的冲突很频繁（比如秒杀抢库存），就该换成悲观锁或者别的手段了。

> **这是选型的关键思路：不要问"哪个更好"，要问"我的场景冲突多不多"。**

## 六、状态机的非法迁移，也是并发保护的一部分

除了乐观锁，状态机本身也提供了一层保护。

考虑这个场景：补偿扫描把任务捡起来重新推进的同时，
用户提交了"取消"请求。

```
扫描线程：     advance(taskId)  →  读到 state = GENERATING
用户请求线程：  cancel(taskId)   →  改成 CANCELLED
```

如果扫描线程在生成完之后，想执行 `fire(GENERATED)`：

```java
// 此时 state 已经是 CANCELLED 了
task.fire(TaskEvent.GENERATED);
// → CANCELLED 是终态，没有任何出边
// → 抛出 IllegalTaskTransitionException
```

**非法迁移被直接拒绝，任务不会被"复活"。**

再加上乐观锁拦住写入，两道防线合起来：

```
第一道：状态机   → 拦截逻辑上不该发生的迁移
第二道：乐观锁   → 拦截并发写入冲突
```

## 七、完整的"重启续跑"流程演示

假设服务器在生成过程中被重启，我们来走一遍全过程：

```
【T1】用户提交任务
      数据库: state = CREATED

【T2】后台线程开始处理
      数据库: state = GENERATING,  updated_at = 20:00:00

【T3】模型正在生成（约需 8 秒）
      ... 此时服务器被重启 ...

=================== 重启分割线 ===================

【T4】服务器起来了
      数据库里依然躺着: state = GENERATING, updated_at = 20:00:00
      但没有线程在跑这个任务

【T5】补偿扫描（每 2 秒一次）
      发现一个 state = GENERATING 的任务
      检查 updated_at：20:00:00，现在已经是 20:00:40
      超过 30 秒阈值 → 判定为"卡住"
      → 提交到线程池重新推进

【T6】advance(taskId) 被调用
      从数据库读出 AiTask（state = GENERATING）
      进入 switch 分支：case GENERATING → generate()
      → 重新调用模型生成
      → 正常往下走

【T7】任务最终完成
      数据库: state = COMPLETED
```

**用户视角**：他只是发现这个任务比平时慢了几十秒，最后还是拿到结果了。
他完全不知道中间服务器重启过。

## 八、这套方案的适用边界

要诚实地说明：**这是单机方案，不是分布式方案。**

| 场景 | 本方案的表现 |
| --- | --- |
| 单机部署，进程重启 | ✅ 能恢复 |
| 单机部署，机器宕机 | ✅ 重启后能恢复 |
| 多实例部署，实例 A 挂了 | ⚠️ 实例 B 的补偿扫描能捡起来，但可能和 A 的残留线程撞车（乐观锁能保证数据不错，但会浪费一次模型调用） |
| 任务量很大（每秒上千） | ❌ 每 2 秒扫 50 条不够用，需要换成消息队列 |

真实的多机方案大致是这样：

```
任务提交 → 写入数据库 + 发一条消息到队列
                    ↓
        多个 worker 从队列消费
                    ↓
        worker 抢任务时用分布式锁（Redis 或数据库行锁）
                    ↓
        处理完更新状态，写回
                    ↓
        定时任务只负责扫描"明显异常"的僵尸任务
```

**为什么本项目不这么做？** 因为那需要引入消息队列，
会让这个以"讲清楚原理"为目标的项目的复杂度大幅上升。

**重要的是知道边界在哪，而不是假装没有边界。**

---

## 九、小结

| 问题 | 解法 | 代码位置 |
| --- | --- | --- |
| 任务进度会丢 | 每一步状态立刻写数据库 | `TaskService.persistInternal()` |
| 重启后没人继续跑 | 定时补偿扫描，捡起停滞任务 | `TaskService.compensateStuckTasks()` |
| 并发修改互相覆盖 | `@Version` 乐观锁 | `AiTaskEntity.version` |
| 可能出现不可能的迁移 | 状态机拒绝非法迁移 | `TaskStateMachine.next()` |

**一句话记住：持久化解决"丢失"，乐观锁解决"冲突"，状态机解决"逻辑错误"。**

三者各管一件事，配合起来才是完整的。
