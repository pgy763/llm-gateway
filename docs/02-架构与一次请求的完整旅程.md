# 02 · 架构与一次请求的完整旅程

## 一、先说什么是"分层"

如果你写过 Spring Boot 项目，大概见过这种结构：

```
controller/    接口
service/       业务逻辑
mapper/        数据库操作
```

这就是分层。但很多项目的分层是"为了看起来像分层"，`service` 里照样直接写 SQL，
`controller` 里照样写业务判断 —— 层与层之间并没有真正分开。

**真正有意义的分层，看的是一件事：依赖方向。**

```
   ┌─────────────────────────────────────┐
   │  api  (接口层)                       │  接收 HTTP 请求
   └────────────────┬────────────────────┘
                    │ 可以依赖 ↓
   ┌────────────────▼────────────────────┐
   │  application (应用层)                │  编排流程
   └────────────────┬────────────────────┘
                    │ 可以依赖 ↓
   ┌────────────────▼────────────────────┐
   │  domain (领域层)                     │  业务规则
   │  ★ 这一层不依赖任何其他层             │
   └────────────────▲────────────────────┘
                    │ 实现 ↓ 上层定义的接口
   ┌────────────────┴────────────────────┐
   │  infrastructure (基础设施层)          │  数据库、缓存
   └─────────────────────────────────────┘
```

关键点：**箭头不能反向。**

`domain`（领域层）里不能出现：
- `@Entity`、`@Repository`（数据库相关）
- `RestTemplate`、`HttpClient`（网络相关）
- `@RestController`（Web 相关）

这一层只描述"业务上什么是对的"，不关心"怎么存、怎么发"。

好处很实在：**这一层可以脱离数据库和网络单独测试。**
比如状态机的规则，几百个测试用例跑完只要 0.1 秒，不需要起 Spring、不需要数据库。

## 二、四层各负责什么

用一个具体的问题来区分：**"上游模型超时了该怎么办？"** 这个决策应该放在哪一层？

| 层 | 负责什么 | 用上面这个问题举例 | 不该做什么 |
| --- | --- | --- | --- |
| **api** | 收发 HTTP，参数校验 | 只会说"调用失败了，返回 503" | 不该决定"要不要重试" |
| **application** | 编排多个模块完成一个用例 | "超时了 → 标记这家不健康 → 试下一家" | 不该写具体的 HTTP 请求代码 |
| **domain** | 业务规则、数据结构 | 定义"什么叫超时"、"错误分几类" | 不该真的去发网络请求 |
| **infrastructure** | 具体技术实现 | 真的用 HttpClient 发请求、真的写 Redis | 不该决定业务上该怎么做 |

判断一个类该放哪层，可以问自己：

> **这个逻辑，换个数据库、换个 HTTP 库，还需要改吗？**
> 不需要改 → 属于 domain
> 需要改 → 属于 infrastructure

## 三、一次普通请求的完整旅程

这是本文最重要的部分。假设前端发来这样一个请求：

```bash
curl -X POST http://localhost:8080/v1/chat \
     -H "X-Api-Key: sk-demo-0001" \
     -d '{"messages":[{"role":"user","content":"你好"}]}'
```

### 第 1 站：接口层接收

**代码位置**：`api/ChatController.java`

```java
@PostMapping
public ApiResponse<ChatResponse> chat(
        @RequestHeader(value = "X-Api-Key", required = false) String apiKey,
        @Valid @RequestBody ChatRequest request) {
    return ApiResponse.ok(chatService.chat(apiKey, request));
}
```

这里只做了三件事：取请求头、校验请求体格式、交给下一层。

`@Valid` 会检查 `messages` 是不是空的（`ChatRequest` 上标了 `@NotEmpty`）。
如果格式就不对，会在这里被拦住，不会浪费一次模型调用。

**这一层做完就结束了，它不知道也不需要知道后面会发生什么。**

---

### 第 2 站：应用层的前置检查 —— 鉴权、限流、配额

**代码位置**：`application/ChatService.java` 的 `prepare()` 方法

```java
private ApiKeyEntity prepare(String apiKey) {
    // ① 鉴权
    ApiKeyEntity keyEntity = apiKeyService.authenticate(apiKey);

    // ② 限流
    if (!rateLimiter.tryAcquire(keyEntity.getKeyValue())) {
        throw BizException.rateLimited("请求过于频繁...");
    }

    // ③ 配额
    if (keyEntity.remainingTokens() <= 0) {
        throw BizException.quotaExceeded("配额已用尽...");
    }

    return keyEntity;
}
```

三件事的顺序是有讲究的：

```
先鉴权  →  因为不知道"你是谁"，就不知道该限谁的流
再限流  →  因为限流检查要读 Redis，比较慢，放在鉴权后面可以少做无用的 IO
最后查配额 →  最简单的一步，放最后
```

**为什么这样排序？** 想象一下如果有坏人拿假密钥刷你：
- 如果先查配额，每次都要查一次数据库，白费力气
- 现在先鉴权，假密钥直接在第一步就被挡住了

> 这就是"把便宜的检查放前面，把昂贵的检查放后面"。

---

### 第 3 站：规划降级链

**代码位置**：`domain/route/RoutePlanner.java`

```java
List<ChatProvider> chain = routePlanner.plan(request.getModel());
```

假设配置了三个提供方，`plan()` 会返回一条有序的链：

```
[deepseek, kimi, mock]
```

规划时会做三件事：

1. **按优先级排序** —— 配置里 DeepSeek 是 1，Kimi 是 2，mock 是 99
2. **剔除当前不健康的** —— 如果 DeepSeek 最近连续失败 3 次了，会被跳过
3. **截断到最大尝试次数** —— 配置里是 3 次，避免一个请求拖太久

---

### 第 4 站：逐个尝试（降级链开始工作）

**代码位置**：`application/ChatService.java` 的 `chat()` 方法

```java
for (ChatProvider provider : chain) {
    String model = providerRegistry.pickModel(provider.name(), request.getModel());
    try {
        ChatResponse response = provider.chat(request, model);
        healthTracker.recordSuccess(provider.name());   // 成功 → 清空失败计数
        // ... 记账、返回
        return finalResponse;
    } catch (ProviderException e) {
        healthTracker.recordFailure(provider.name());   // 失败 → 累加失败计数
        if (!e.isRetryable()) {
            break;      // 换一家也没用的错误，不必继续
        }
    }
}
```

注意两个细节：

**细节一**：`pickModel` 会把模型名换掉。

主模型是 `deepseek-chat`，降级到 Kimi 时必须换成 `moonshot-v1-8k`。
如果偷懒直接透传，Kimi 会返回 400（"我不认识这个模型"），降级就白做了。

**细节二**：不是所有错误都重试。

`e.isRetryable()` 这个判断来自 `ProviderException`。
400（参数错）和 401（密钥无效）这类错误，换一家也是一样的结果，
继续重试只是白白烧掉别家的额度。

---

### 第 5 站：记账

**代码位置**：`application/MeteringService.java`

```java
usageLogRepository.save(日志记录);              // 写一条调用明细
apiKeyRepository.findById(id).ifPresent(key -> {
    key.consume(usage.getTotalTokens());       // 累加已用量
    apiKeyRepository.save(key);
});
```

这一步有个刻意的设计：**记账失败不影响主流程。**

```java
private void save(UsageLogEntity entity) {
    try {
        usageLogRepository.save(entity);
    } catch (Exception e) {
        log.error("写入调用日志失败，requestId={}", entity.getRequestId(), e);
        // 注意：这里吞掉了异常，没有往上抛
    }
}
```

为什么？因为用户已经拿到回答了。
不能因为"日志写不进去"这种辅助功能出问题，就把一次成功的调用变成失败。

> 这类判断在真实项目里很常见，原则是：
> **辅助功能不能反过来影响主功能。**

---

### 第 6 站：返回

回到 `ChatController`，`ApiResponse.ok(...)` 把结果包成统一格式返回。

整个旅程走完了。**大模型真正被调用的那一刻，只是这六站中的一小段**（第 4 站里的一行 `provider.chat()`）。

## 四、流式请求的旅程（有什么不一样）

**代码位置**：`application/ChatService.java` 的 `chatStream()` 和 `streamWithFallback()`

流式请求前面三站完全一样，从第 4 站开始分岔：

```
普通请求：  等模型全部写完 → 一次性返回 → HTTP 线程释放

流式请求：  把任务丢给后台线程 → HTTP 线程立刻释放（返回 SseEmitter）
            后台线程：模型每吐一个字 → 立刻推给客户端
```

为什么要这样？因为一次生成要十几秒。
如果让 HTTP 线程一直等着，这个线程就被占住了，并发量上不去。

**流式有一个普通请求没有的难题：**

```
场景：已经推了 200 个字给用户，此时上游断了

  ┌─ 能不能换个模型接着往下写？
  │
  └─ 不能。两个模型写的上下文接不上，
     用户会看到前后矛盾的两段内容。
```

所以代码里专门记了一个标志：

```java
AtomicBoolean alreadyEmitted = new AtomicBoolean(false);

TokenUsage usage = provider.chatStream(request, model, delta -> {
    alreadyEmitted.set(true);         // 记下"已经吐过内容了"
    sendEvent(emitter, "delta", Map.of("text", delta));
});

// ...catch 块里：
if (alreadyEmitted.get()) {
    // 已经输出过了，不能再降级，只能如实报错
    sendEvent(emitter, "error", Map.of("message", "生成过程中断..."));
    emitter.complete();
    return;
}
```

> 这是"降级"这个策略的**边界**。
> 降级的前提是"这次尝试可以完整重来"。
> 一旦输出对外产生了影响（用户已经看到了半截内容），就无法回退了。
>
> 这类"副作用不可逆"的判断，是分布式系统里很常见的一类思考。

## 五、任务请求的旅程（完全不同的路径）

**代码位置**：`application/TaskService.java`

提交任务的接口**几毫秒就返回了**，因为真正的处理是异步的：

```
HTTP 线程：
  ├─ 鉴权
  ├─ 创建任务记录（状态 CREATED）→ 写数据库
  ├─ 提交到线程池
  └─ 立刻返回任务号 ──────────────→ 用户拿到 "task-abc123"

后台线程（异步，可能要跑十几秒）：
  ├─ CREATED    → GENERATING   开始处理
  ├─ GENERATING → 调模型       写初稿
  ├─ REVIEWING  → 按规则审查
  ├─ 不合格     → RETRYING → GENERATING（重写，最多 2 次）
  ├─ 合格       → FINALIZING → COMPLETED
  └─ 每一步都立刻写数据库
```

**为什么要立刻写数据库？** 这是"断点续跑"的关键。

假设在第 3 步（审查中）时服务器被重启了。重启后：

- 内存里什么都没有了
- 但数据库里记着"这个任务当前状态是 REVIEWING"
- 定时补偿任务扫到它，重新推进 → 任务继续往下走

详见 [05-断点续跑与并发控制](05-断点续跑与并发控制.md)。

## 六、代码目录与层的对应关系

```
src/main/java/com/pgy/gateway/
│
├── api/                        ← 接口层
│   ├── ChatController.java
│   ├── TaskController.java
│   ├── AdminController.java
│   └── dto/                    （返回给调用方的数据结构）
│
├── application/                ← 应用层
│   ├── ChatService.java            对话主流程
│   ├── TaskService.java            任务状态机推进
│   ├── ApiKeyService.java
│   ├── MeteringService.java
│   └── StatsService.java
│
├── domain/                     ← 领域层（不依赖任何其他层）
│   ├── chat/                      消息、请求、响应的数据结构
│   ├── provider/                  ★ 适配器接口与实现
│   │   ├── ChatProvider.java          接口（关键抽象）
│   │   ├── OpenAiCompatibleProvider   真实厂商适配
│   │   └── MockProvider               模拟厂商
│   ├── route/                     路由与降级
│   └── task/                      ★ 状态机（核心）
│
├── infrastructure/             ← 基础设施层
│   ├── persistence/               数据库实体与 Repository
│   ├── ratelimit/                 令牌桶限流
│   └── health/                    健康状态（Redis 实现）
│
└── config/                     配置类
```

**一个观察点**：`domain/provider/ChatProvider.java` 是一个接口，
它的两个实现（真实厂商 / 模拟厂商）都在同一个包里。

而 `domain/route/ProviderHealthTracker.java` 是一个接口，
它的实现在 `infrastructure/health/` 里 —— 因为它依赖 Redis。

> 接口放哪，取决于"它描述的是业务概念还是技术手段"。
> "提供方"是业务概念 → 放 domain。
> "用 Redis 记健康状态"是技术手段 → 实现放 infrastructure。

## 七、小结

| 层 | 一句话职责 | 关键类 |
| --- | --- | --- |
| api | 收发 HTTP | `ChatController` |
| application | 编排流程 | `ChatService`、`TaskService` |
| domain | 业务规则 | `TaskStateMachine`、`ChatProvider` |
| infrastructure | 技术实现 | `RedisProviderHealthTracker`、`OpenAiCompatibleProvider` |

**一句话记住这个架构的设计意图：**

> 让"业务规则"和"技术手段"互不干扰。
> 换数据库不影响规则，改规则不影响数据库。
