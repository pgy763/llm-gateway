# 01 · 项目背景：为什么需要一个大模型网关

## 先说结论

这个项目做的事情，用一句话说就是：

> **把"调用大模型"从"每个系统各干各的"，改成"统一走一个入口"。**

听起来很简单，简单到你会怀疑"这值得单独做一个系统吗"。

下面用一个具体场景讲清楚为什么值得。

---

## 一、一个正在发生的场景

假设你是"小满科技"的后端工程师。公司不大，二十来个人，但从今年春天开始猛推 AI 功能。

三个月时间里，公司陆续上线了 5 个用到 AI 的功能：

| 功能 | 谁做的 | 怎么实现的 |
| --- | --- | --- |
| 客服自动回复 | 你 | 前端传一段客户问题，后端调 DeepSeek，返回话术 |
| 商品文案批量生成 | 运营同事找你帮忙 | 又一个接口，还是调 DeepSeek |
| 数据报表转人话 | 数据同事自己写的脚本 | Python 脚本里直接调 |
| 周报自动摘要 | 另一个后端 | 用的是 Kimi，因为他觉得便宜 |
| AI 智能搜索（试验中） | 你和实习生 | 调 DeepSeek，但参数经常调 |

每个功能上线的时候都很顺利。**问题是从第三个月开始暴露的。**

---

## 二、五个坑，一个比一个疼

### 坑 1：密钥满天飞

三个月后你突然发现，那个 DeepSeek 的 API Key 出现在这些地方：

- 你的项目 `application.yml` 里
- 运营那个功能的配置文件里
- 数据同事的 Python 脚本里（**而且他把它提交到 Git 了**）
- 另一个后端的代码里
- 实习生本地电脑的一个 `.txt` 文件里

现在问题来了：

- 运维说这个 Key 可能泄露了，要换 → **你得挨个通知 5 个人，改 5 个地方，还得重新部署**
- 数据同事试用期结束离职了 → **他电脑里那份 Key 还在，但你不知道他还有没有别的备份**
- 老板问"咱们一共申请了几个 Key" → **你答不上来**

**根本原因**：密钥是"凭据"，凭据一旦被复制到多处，就再也收不回来了。

---

### 坑 2：挂一家，全挂

某个周二下午，DeepSeek 官方的 API 出现大规模故障，持续了 40 分钟。

这 40 分钟里：

- 客服自动回复 → 完全不可用，客户消息没人回
- 商品文案生成 → 不可用
- 数据报表 → 不可用
- AI 搜索 → 不可用

只有周报摘要那个功能还活着（因为它用的是 Kimi）。

老板在群里问："能不能切到别家？"

你想了想：能，但要改代码、重新测试、重新部署，**最快也得半小时**。而故障可能十分钟后就恢复了。

最后大家的处理方式是：**等着**。

**根本原因**：没有"备胎"。每家系统只绑死了一家厂商，厂商挂了就是系统挂了。

---

### 坑 3：花了多少钱，说不清

月底，财务把 DeepSeek 的账单发到群里：**3400 元**。

老板问："这钱花在哪了？"

你打开 DeepSeek 的后台，只能看到一个总数。它只知道"有一个 Key 产生了这些调用"，**它不知道你那 5 个功能各花了多少**。

因为你只有一个 Key，5 个功能共用。

于是你只能猜："客服回复量最大，应该是它花的……吧？"

**根本原因**：计量粒度和业务维度对不上。厂商按 Key 计费，但你想按"功能"或"团队"看成本。

---

### 坑 4：被刷了才知道

某个周五晚上，AI 智能搜索那个试验功能被人发现了。

第二天早上你醒来，发现：

- 那个接口一晚上被调用了 **8 万次**
- 烧掉了接近一个月的预算
- 日志里全是同一个 IP 在循环请求

为什么没人拦？

因为那个功能是"试验中"，**谁都没想起来给它加限流**。

**根本原因**：限流这种"基础设施级别的事情"，如果让每个功能自己实现，就一定会有人漏掉——尤其是赶进度的试验功能。

---

### 坑 5：长任务说丢就丢

产品经理提了个需求："能不能加个功能，用户输入一个主题，自动生成一份完整的行业分析报告？"

你评估了一下：一份报告要经过"搜集要点 → 搭大纲 → 分段生成 → 通读润色"好几步，中途要调好几次模型，总共大概两分钟。

你实现了，测试也通过了。

然后上线第二天，运维半夜做了一次服务器重启（常规维护）。

**所有正在生成中的报告，全部消失了。**

用户看到的现象是：进度条一直卡在 60%，永远不动。

**根本原因**：任务进度只存在于内存里。进程一重启，内存清空，进度就没了。

---

## 三、把五个坑放在一起看

注意这五个坑有一个共同特点：

> **它们都不是业务逻辑问题，而是"基础设施"问题。**

业务逻辑是"客户问什么我就答什么"。上面这些跟业务一点关系都没有，全是"怎么调用"、"调用失败了怎么办"、"谁在调用"、"花了多少"。

这类问题的麻烦在于：**它必须每个系统都处理一遍**。而只要有一个系统漏了，坑就出现了（比如坑 4 就是漏了限流的后果）。

---

## 四、解决思路：抽出中间层

既然每个系统都要处理同样的问题，那就**只处理一次**，把公共部分抽出来，做成一个独立的服务。

所有业务系统不再直接调用模型厂商，而是调用这个中间层：

```
   修改前：每个系统直连厂商

   客服系统 ──────────────→ DeepSeek
   运营系统 ──────────────→ DeepSeek
   数据脚本 ──────────────→ DeepSeek
   周报功能 ──────────────→ Kimi
   AI 搜索  ──────────────→ DeepSeek


   修改后：所有系统走网关

                          ┌──────────────────┐
   客服系统 ──┐           │                  │
   运营系统 ──┤           │   LLM Gateway    │──→ DeepSeek
   数据脚本 ──┼──────────→│                  │
   周报功能 ──┤           │  鉴权 / 限流      │──→ Kimi
   AI 搜索  ──┘           │  路由 / 降级      │
                          │  记账 / 编排      │──→ 兜底模型
                          └──────────────────┘
```

这个中间层，业内就叫**网关（Gateway）**。

> **类比**：这就像公司的总机。
> 以前每个员工都把自己的手机号给客户，客户直接打手机。
> 员工离职、换号、休假，客户就找不到人了。
> 现在客户统一打总机，总机负责转到合适的人 —— 谁休假、谁离职，客户完全不用管。

---

## 五、五个坑是怎么被填上的

| 坑 | 网关怎么解决 |
| --- | --- |
| **1. 密钥满天飞** | 业务系统拿到的不是真密钥，而是网关签发的**虚拟密钥**。真密钥只存在网关一处，要换只换一个地方 |
| **2. 挂一家全挂** | 配置一条**降级链**：DeepSeek 失败自动切 Kimi，再失败切兜底模型。业务侧完全无感知 |
| **3. 花多少说不清** | 每次调用都**记账**，按虚拟密钥统计 token。哪个部门花了多少，一查就知道 |
| **4. 被刷了才知道** | **限流**做在网关上，是统一的，不存在"某个功能忘了加"的情况 |
| **5. 长任务会丢** | 多步任务用**状态机**管理，状态写进数据库。重启后自动接着跑 |

> 前 4 个坑是"代理"型需求（帮你转发、帮你拦、帮你记账），
> 第 5 个坑是"编排"型需求（帮你管流程）。
> 这个项目两部分都做了，这也是它比单纯的"反向代理"更有意思的地方。

---

## 六、诚实地说：网关也有代价

任何架构方案都有代价。如果只讲好处不讲代价，那是宣传而不是设计。

引入网关之后，你会多出这些东西：

| 代价 | 说明 | 怎么缓解 |
| --- | --- | --- |
| **多了一跳** | 请求要经过网关再转发，理论上多几毫秒延迟 | 网关本身很轻，实测增加通常不到 5ms |
| **多了一个要维护的服务** | 它挂了，所有 AI 功能一起挂 | 无状态设计，可以水平扩多个实例 |
| **需要额外限流** | 现在业务系统都打网关，网关自己不能被打挂 | 网关内部有令牌桶，且限流是按密钥维度的 |
| **初期开发成本** | 做这个网关本身要花时间 | 一次投入，五个系统都不用再各写一遍 |

**所以网关并不总是必要的。** 判断标准很简单：

- 只有 1 个系统用 AI → **不需要**，直连就行，别过度设计
- 有 3 个以上系统用，或者有对外提供服务 → **值得做**
- 有多个团队共用同一个预算 → **应该做**
