# 04 · 降级、熔断与限流

这篇讲三个"保护措施"。它们的共同点是：**都不是为了让功能更强，而是为了让系统在出问题时别垮得太难看。**

---

## 一、降级：一家不行就换一家

### 什么是降级

```
用户请求 → 试 DeepSeek → 失败了 → 试 Kimi → 成功了 → 返回给用户
```

用户全程无感知。他甚至不知道中间失败过一次。

这就是**降级**：主方案不可用时，自动退到备用方案。

**注意"降级"这个词的含义**：备用方案通常比主方案差一点（比如慢一点、贵一点、质量低一点），
所以叫"降级"。但**有总比没有好**。

### 降级链是怎么排出来的

配置里每家提供方有一个 `priority`：

```yaml
gateway:
  providers:
    - name: deepseek
      priority: 1        # 最优先
    - name: kimi
      priority: 2        # 备选
    - name: mock
      priority: 99       # 兜底
```

排序后就形成一条链：`[deepseek, kimi, mock]`。

代码在 `domain/route/RoutePlanner.java`：

```java
List<ChatProvider> healthy = registry.all().stream()
        .filter(provider -> !healthTracker.isUnhealthy(provider.name()))   // 剔除熔断的
        .toList();
// ...按优先级取前 N 个
```

### 一个容易漏掉的细节：降级时要换模型名

主模型是 `deepseek-chat`，降级到 Kimi 时，**模型名必须换掉**。

如果不换，Kimi 收到 `deepseek-chat` 会返回 400（"我不认识这个模型"），
降级就白做了。

```java
// domain/provider/ProviderRegistry.java
public String pickModel(String providerName, String requestedModel) {
    ProviderConfig config = configOf(providerName);

    // 调用方指定的模型，这家支持 → 就用指定的
    if (requestedModel != null && config.getModels().contains(requestedModel)) {
        return requestedModel;
    }
    // 否则用这家的第一个模型
    return config.getModels().get(0);
}
```

> 这类细节很容易被忽略，但恰恰是"能跑通"和"跑不通"的区别。

## 二、什么错误该重试，什么不该

这是降级策略里**最容易做错**的一点。

如果无脑重试，会遇到这种情况：

```
用户传了个错误的参数
  → DeepSeek 返回 400
  → 换 Kimi，Kimi 也返回 400
  → 换 mock，mock 兜住了

结果：用户的参数错误被掩盖了，而且白烧了两家的额度
```

所以必须区分错误类型。代码在 `domain/provider/ProviderException.java`：

```java
private final boolean retryable;    // 这个错误"换一家可能就好了"吗？
```

判断逻辑在 `OpenAiCompatibleProvider.toProviderException()`：

```java
private ProviderException toProviderException(int statusCode, String body) {
    boolean retryable = statusCode == 429 || statusCode >= 500;
    return new ProviderException(name(), message, retryable, null);
}
```

完整对照表：

| 上游返回 | retryable | 为什么 |
| --- | --- | --- |
| 连接超时 / 读超时 | ✅ 是 | 对方可能只是临时网络抖动 |
| **429** Too Many Requests | ✅ 是 | 这家限流了，换一家立刻就能成 |
| **500 / 502 / 503 / 504** | ✅ 是 | 服务端自己的问题，换一家可能没事 |
| **400** Bad Request | ❌ 否 | **请求本身写错了，换一家也是一样的错** |
| **401** Unauthorized | ❌ 否 | **密钥无效，换一家也是无效** |
| **403** Forbidden | ❌ 否 | 权限不够，换一家也一样 |

> **判断原则：这个错误是"对方的"还是"我的"？**
> 对方的（它挂了、它限流了）→ 换一家试试
> 我的（参数错了、密钥错了）→ 别试了，直接告诉调用方

## 三、熔断：别让用户陪着等超时

### 光有降级还不够

假设 DeepSeek 挂了，而它的超时设置是 60 秒。那么：

```
用户 A 的请求：
  → 试 DeepSeek ... 等 60 秒 ... 超时
  → 试 Kimi ... 0.8 秒 ... 成功
  总共：60.8 秒

用户 B 的请求：
  → 试 DeepSeek ... 又等 60 秒 ...
  → 试 Kimi ... 成功
  总共：60.8 秒
```

**每次请求都要先白等 60 秒**，这比直接失败还难受。

### 熔断的做法

记住"连续失败次数"，超过阈值就暂时拉黑：

```java
// infrastructure/health/RedisProviderHealthTracker.java

@Override
public boolean isUnhealthy(String providerName) {
    String value = redisTemplate.opsForValue().get(key(providerName));
    if (value == null) {
        return false;
    }
    return Integer.parseInt(value) >= properties.getRoute().getUnhealthyThreshold();
}

@Override
public void recordFailure(String providerName) {
    String key = key(providerName);
    Long count = redisTemplate.opsForValue().increment(key);
    // 第一次失败时设置过期时间 = 冷却期
    if (count != null && count == 1L) {
        redisTemplate.expire(key, Duration.ofSeconds(cooldownSeconds));
    }
}
```

行为是这样的：

```
DeepSeek 开始失败
  ├─ 失败 1 次   → 计数 = 1，设置 30 秒过期
  ├─ 失败 2 次   → 计数 = 2
  ├─ 失败 3 次   → 计数 = 3  → 达到阈值，标记为"不健康"
  └─ 之后的请求  → 直接跳过 DeepSeek，从 Kimi 开始试（用户不再白等）

30 秒后 key 过期，计数清零
  └─ 下次请求重新尝试 DeepSeek —— 万一它已经恢复了
```

**"冷却期过后自动恢复"这一点很重要。** 如果没有它，
一次误判就会让这家提供方被永久排除，得手动重启才能恢复。

### 为什么熔断状态要放 Redis，不放本地 Map

因为网关通常部署多个实例：

```
         ┌─ 实例 A ─┐
请求 ────┤          ├──── 如果各存各的：
         └─ 实例 B ─┘     A 发现 DeepSeek 挂了，B 还不知道，继续往那边发
```

放 Redis 里，所有实例共享同一个判断。

### 一个刻意的取舍：Redis 挂了怎么办

看这段代码：

```java
try {
    String value = redisTemplate.opsForValue().get(key(providerName));
    // ...
} catch (Exception e) {
    // Redis 挂了不能导致网关整体不可用 —— 保守地认为"健康"
    log.warn("读取提供方健康状态失败，本次按健康处理：{}", e.getMessage());
    return false;
}
```

**Redis 出问题时，代码选择"认为这家是健康的"。**

这叫 **fail-open**（故障时放行）。对应的另一个选择是 fail-close（故障时拒绝一切）。

为什么选 fail-open？

因为"健康检查"只是**优化手段**，不是必需功能。
它的作用是让请求快一点，不是让请求能成功。

如果因为 Redis 挂了就拒绝所有请求，等于把一个非核心功能的故障
放大成了整个系统的故障。**本末倒置了。**

> 这个判断原则可以用在很多地方：
> **辅助功能故障时，要退化成"没有它也能跑"，而不是"整个不能用"。**

## 四、限流：为什么不能简单数数

### 需求是什么

"每个密钥每分钟最多 60 次请求"。

最直觉的实现：

```java
// 伪代码
if (redis.incr(key) == 1) {
    redis.expire(key, 60);      // 60 秒窗口
}
if (redis.get(key) > 60) {
    reject();
}
```

### 问题：临界突发

这个计数器有个漏洞。看时间轴：

```
12:00:59.900   第 59 次请求  → 计数 59
12:00:59.990   第 60 次请求  → 计数 60
12:01:00.000   ← 窗口重置，计数归 0
12:01:00.010   第 1 次请求   → 计数 1
12:01:00.100   第 2 次请求   → 计数 2
...
12:01:00.500   第 30 次请求  → 计数 30
```

**在 0.6 秒内，系统承受了 90 次请求**（59+60 的后半段 + 30）。

对上游来说，这就是一次真实的突发流量。计数器算法在窗口切换的瞬间是失效的。

### 令牌桶怎么解决

换个模型想象：

```
有一个桶，容量是 20 个令牌（capacity）
每秒钟往桶里滴 5 个令牌（refillPerSecond）
桶满了就不再往里滴

每个请求进来，先看桶里有没有令牌
  有 → 拿走 1 个，放行
  没有 → 拒绝（429）
```

这个模型的两个关键性质：

| 性质 | 说明 |
| --- | --- |
| **长期速率被限制** | 令牌每秒只滴 5 个，所以长期平均速率不可能超过 5/秒 |
| **允许短时突发** | 桶里攒了 20 个令牌，所以可以瞬间放行 20 个请求 |

**这不是漏洞，这是特性。** 真实业务里流量本来就不是匀速的 ——
用户点击有高峰低谷，攒着的令牌正好用来吸收这些正常波动。

而上面那个"临界突发 90 次"的问题，令牌桶不会有 ——
因为令牌是真的"生产"出来的，不会因为时间窗口切换而凭空多出来。

### 为什么算法要写在 Lua 里

看这个逻辑：

```
① 读出桶里现在有几个令牌
② 判断够不够
③ 扣减
④ 写回
```

这四步如果分成四条 Redis 命令发出去，会有并发问题：

```
线程 A：① 读到 1 个令牌 → ② 判断够用
线程 B：① 读到 1 个令牌 → ② 判断够用
线程 A：③ 扣减 → 写回 0
线程 B：③ 扣减 → 写回 0

结果：只剩 1 个令牌，却放行了 2 个请求。
```

**Redis 执行 Lua 脚本是原子的** —— 脚本执行期间不会被其他命令打断。
把这几步塞进一个 Lua 脚本，上面这个问题就消失了。

代码在 `resources/lua/token_bucket.lua`，核心部分：

```lua
local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'lastRefill')
local tokens = tonumber(bucket[1])
local lastRefill = tonumber(bucket[2])

-- 第一次访问：桶装满
if tokens == nil then
    tokens = capacity
    lastRefill = now
end

-- 按时间差补充令牌
local elapsed = now - lastRefill
tokens = math.min(capacity, tokens + elapsed * refillRate / 1000)

-- 判断是否放行
local allowed = 0
if tokens >= requested then
    tokens = tokens - requested
    allowed = 1
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'lastRefill', now)
redis.call('EXPIRE', KEYS[1], ttl)
return allowed
```

### 限流维度：为什么按"密钥"而不是按 IP

因为限流的目的**不是防攻击**（那是 WAF 的活），而是**控制成本**。

- 按 IP 限：一个公司内网几十个人共用一个出口 IP，会互相影响
- 按密钥限：**每个业务方各自一个桶，谁刷爆自己的桶不影响别人**

这跟"成本分摊"的目标是一致的：客服系统用得多是正常的，
但它不应该把运营系统的额度挤掉。

### 同样采用 fail-open

```java
} catch (Exception e) {
    // fail-open：限流是保护措施，不能让它反过来成为单点故障。
    // Redis 出问题时放行请求，最多是短暂失去限流能力，但服务本身是活的。
    log.warn("限流检查失败，本次放行：{}", e.getMessage());
    return true;
}
```

理由和健康检查一样。**代价是：Redis 挂掉期间，限流是失效的。**

这个代价能接受吗？

对于这个场景，能接受。因为：
1. Redis 故障本身是低概率事件
2. 配额检查（查数据库）还在，最坏情况也不会花超配额
3. 反过来说，如果 fail-close，Redis 一挂所有 AI 功能全停 —— 这个代价大得多

> 这就是工程里的"两害相权取其轻"。
> 没有绝对正确的选择，只有"针对这个场景更合适的"选择。

## 五、三个措施的关系

```
一个请求进来
    │
    ▼
┌─────────────┐
│  ① 限流      │  还没开始干活，先看你有没有资格用
│  （令牌桶）   │  拒绝 → 429，你不是我们的目标用户场景
└──────┬──────┘
       │ 通过
       ▼
┌─────────────┐
│  ② 路由      │  决定去试哪几家，跳过被熔断的
│  （降级链）   │  ← 熔断状态在这里被读取
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  ③ 调用上游   │  失败了吗？
│             │    可重试 → 回 ②，试下一家（这就是降级）
│             │    不可重试 → 直接失败
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  ④ 更新健康   │  成功 → 失败计数清零
│     状态     │  失败 → 计数 +1，够了就熔断
└─────────────┘
```

**注意 ②④ 形成的闭环**：熔断状态影响路由选择，路由的结果又更新熔断状态。

这三者合起来，才构成一个"能自己扛住上游故障"的系统。

## 六、可以自己动手验证的点

| 想验证什么 | 怎么做 |
| --- | --- |
| 降级链真的会切换 | 请求模型 `mock-flaky`（前两次必定失败），观察响应里的 `fallbackUsed: true` |
| 熔断真的会生效 | 连续请求 `mock-flaky` 三次以上，观察日志里 DeepSeek/Kimi 被跳过的记录 |
| 限流真的会拦 | 快速连续发 30 个请求（桶容量 20），后面的会返回 429 |
| 不健康会冷却恢复 | 触发熔断后等 30 秒，再请求，观察它是否重新尝试 |

快速压测的小脚本：

```bash
for i in $(seq 1 30); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST http://localhost:8080/v1/chat \
    -H "X-Api-Key: sk-demo-0001" \
    -H "Content-Type: application/json" \
    -d '{"messages":[{"role":"user","content":"test"}]}'
done
```

前 20 个左右应该是 200，后面开始出现 429。
